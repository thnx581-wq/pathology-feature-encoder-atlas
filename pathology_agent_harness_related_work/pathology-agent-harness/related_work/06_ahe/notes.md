# AHE — 自进化的是 harness，而不一定是大模型

**阅读版本：2604.25850v4，2026 年预印本。NOT_RUN。**
论文：*Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses*。

## 原文事实

AHE 固定基础模型，把运行轨迹转换为有来源的分析，修改系统提示、工具、middleware、skills 或记忆等 harness 组件，并用下一轮评估检验改动。[P]
其公开 README 明示 Agent Debugger 仅部分开源；运行还依赖 API、沙箱等设施。[C]
它研究的是编码 agent，不是已经在病理中完成验证的方法。

## 研究问题

只优化回答或一段 prompt，可能无法修复工具实现、状态管理和终止检查的问题。[P]
你关心的科研 workflow 也可能有类似结构性错误：例如训练正确但报告引用了上一轮预测。
这是迁移类比，不能仅凭类比认定该方法在病理中有效。

## 核心机制怎样理解

一类记录说明系统哪些文件/组件可改；一类记录保存任务如何失败；一类记录说明某个改动预期修复什么。
后续真实执行再验证改进与回退。[P]

本调研建议把一次候选更新限制为一条规则或一个工具合同改动。
保留原版本和差异，记录受益任务与退步任务；没有独立再测的“经验总结”不能直接升级为长期 skill。

## 主结果与泛化必须分开

Terminal-Bench 89 个任务参与进化，69.7%→77.0% 是该优化目标上的结果；冻结后的 SWE-bench-verified 迁移另行评测。[P]
不要把优化集重复测试当作未见任务泛化，也不要将 README 后续使用其他模型的排行榜数字混入 v4 主表。

## 能否解决问题

原文说明 harness 组件可以成为有用的适应对象，但组件叠加可能相互干扰，自报归因也可能漏掉回退。[P]
本调研判断：在病理应用中，需要先有强的独立 verifier；否则 agent 可能学会绕过检查而不是真正修复任务。
能解释“为什么这次要改”不等于能预测“会破坏哪里”。

## 技术栈与学习成本

作者实现涉及 NexAU、轨迹分析、API 控制与 E2B 沙箱；部分 debugger 未完整公开。[C]
这些不是入门前置条件。先用本地白名单工具、状态文件、独立检查和单条更新即可研究缩小版闭环。
免训练 LLM 不等于免成本；还需统计用于调试、分析和多轮再测的 API 消耗。

## 建议的 pathology 迁移实验（未执行）

先获得 B1/B2 的真实失败，再将开发任务分为更新来源与独立验证两组。
分别比较不更新、人工规则更新、静态经验库、模型提出候选改动。
禁止改动测试标签、测试配置、评分器和预算；不得删除失败任务。
正式盲测时冻结全部 memory/skills，以同预算任务完成和回退率评价。

一次只允许一个修改，可以降低归因混淆，但可能限制效率；这也是需要权衡并报告的设计选择。
不能只挑通过率最高的一轮而不报告选择过程。

## 对你当前阶段的建议

放在学习路线后段。先理解工具和日志，跑出可重复失败，再讨论 self-evolution。
否则系统“自我反思”的内容无法被证伪，容易只生成听起来合理的建议。
